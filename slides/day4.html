Hidden state

Four ways a notebook stops being repeatable

The clock

A prepared_at column from now(): every run is new bytes.

State changed in place

Population multiplied by 1.01 inside a cell: run it twice, grow twice.

Unseeded randomness

A shuffle before keeping the first copy: a different copy each run.

Unordered iteration

Columns from a set of strings: the order follows Python's hash seed.

What goes wrong. None of the four raises an error; the figure is simply different, and nobody can say which one is right.

Others to mention: multi-threaded engines returning rows in a different order, reading "the latest file" from a folder, and an unpinned package upgrade. The pipeline's steps avoid all of them: the extract date is a parameter, nothing samples, every output is sorted, and DuckDB runs on one thread.

Each step names its inputs and outputs and returns its counts

Every step returns rows_in, rows_out and its parameters: the run log is made of these.

Publish writes to a temporary name and renames: a reader never sees a half-written file. The gate sits before anything is typed or joined, so a bad value fails a rule instead of a cast.

Which change makes the step repeatable?

A dedupe cell shuffles the complaints with df.sample(frac=1), then keeps the first copy of each customer, merchant and product. Two runs keep different copies. What is the fix?

Sort by received date and complaint id, then keep the first: a rule anyone can state
Add random_state=1 to the shuffle
Run the cell only once per month
Remove the dedupe step

Lab 4.2, evidence that it works

Run it from a clean checkout, not from your own folder

  • git clone into an empty folder, then run there.
  • A forgotten file or a package only you have breaks the clone, not your folder.
  • In the lab, the clone published the same bytes as the working folder, and stopped on the seeded extract.
- run: uv sync --locked
- run: uv run run.py --raw ../data/sources_clean ...
- run: |
    uv run run.py --raw ../data/sources ...
    test $? -eq 2

The CI workflow does on every push what task 3 does by hand: installs the pinned versions, publishes on clean data, expects exit 2 on the seeded extract and checks nothing was published. It lives in pipeline/ci/ as course material; in a pipeline's own repository it goes in .github/workflows/.

Lab 4.3, the decision

Neither: the corrected figure is 49.53

  • Keep the late arrivals and the 2026.2 population.
  • De-duplicate resubmissions only: same customer, merchant and product within one day.
  • R04: 324 complaints, 49.53 per 100,000.
  • All 13 regions' October figures were off by more than 1%; R04 by 21%.

The incident note

What happened, root cause, other changes, affected outputs, correction, the answer to the stakeholder, prevention.

The answer to the office: "September's figure missed late arrivals; October's dropped real complaints; the corrected figure is 49.53, republished with a note." The prevention item: a lineage check that warns when a step's parameters change between runs (the stretch of Lab 4.3).

Checkpoint

How do you find which change moved the figure?

Between two runs, the extract gained 260 rows, the population table changed and the dedupe key changed. R04's rate fell from 48.06 to 39.14. How do you attribute the fall?

Blame the extract: it changed the most rows
Divide the fall equally among the three changes
Re-run October and see whether it repeats
Start from September and apply the changes one at a time, recomputing each time
Why. Changes can push in opposite directions; only recomputing one at a time shows each one's share, here a fall of 11.01 from the new key.

Answer: D. C would give 39.14 again: the pipeline is deterministic, which is what makes the attribution possible.

Same bytes twice
