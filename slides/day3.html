What a rule must state

A rule names its owner, dimension, attributes and threshold

dict(id="C01", dimension="completeness",
     owner="Hatoon Al-Furaih",
     table="complaints",
     description="Every complaint has a region: "
                 "the rate is published by region",
     attributes=["region_code"],
     severity="quarantine", max_rate=0.03,
     sql="SELECT rid FROM complaints WHERE "
         "region_code IS NULL OR trim(region_code) = ''")

Owner

Who accepts the threshold and answers when the rule fires.

Business description

Why the figure needs it, in the user's words.

Threshold

The share of failing rows the owner accepts.

The NDMO Data Quality domain asks each data-quality rule to identify its owner, describe the business requirement, assign a dimension, list the attributes and define the metric. Bayyin's rules carry exactly those fields. The owners: Hatoon uses the rate, Abdulelah runs the pipeline, Khulood leads labelling.

One shape for every rule

A rule is a query that returns the failing rows

SELECT rid FROM complaints
WHERE coalesce(closed_date, '') <> ''
  AND TRY_CAST(closed_date AS DATE)
    < TRY_CAST(received_date AS DATE)
  • The same query counts failures, lists them and moves them to quarantine.
  • Every table gets a row id, rid, so a failing row can be named.
  • Rules run on text: a bad value fails the rule, not the load.

K01 is the participants' first exercise in Lab 3.2. TRY_CAST returns NULL instead of an error, so a malformed date does not stop the rule run; V03 catches malformed or future received dates separately.

What happens when a rule fails

Warn, quarantine or block

Warnlog it; the run goes on
→
Quarantineset the failing rows aside with the rule id; stop above the threshold
→
Blockstop before anything is published
Choosing. Quarantine when the remaining rows are still right; block when the error could be in rows that look fine.

A missing region affects only that row: quarantine it and publish the rest. A unit error in a batch may affect rows the rule cannot see: block. The threshold on a quarantine rule protects against quarantining so many rows that the published figure becomes unrepresentative.

The same checks in a framework

A validation library expresses the same rules as a schema

pa.DataFrameSchema({
  "complaint_id": pa.Column(str, unique=True),
  "category_code": pa.Column(str,
      pa.Check.isin(SIX)),
  "amount_sar": pa.Column(float,
      pa.Check.le(50000), nullable=True),
})
  • Finds the same failures: 120 rows in duplicated ids, 170 codes, 619 amounts.
  • Keeps owners, severities and thresholds outside the schema: you still need them.
  • The SQL rules run where the data is; the schema runs where the DataFrame is.

Pandera counts both copies of a duplicated id (120), the SQL rule counts the second copy only (60). Either is fine if the report says which. Frameworks such as Pandera, Great Expectations or Soda are worth using; none of them decides the owner or the threshold for you.

A data contract

A contract writes down what the consumer relies on

Producer: Abdulelah

Runs the preparation pipeline and publishes complaints_prepared. Runs the contract before publishing.

Consumer: Hatoon

Builds the monthly rate from it. Agrees the clauses; can run the contract on arrival.

What goes wrong. Without a contract, a renamed column breaks the report on the morning it is due, and nobody knew it was relied on.

The rules of Session 2 gate the raw extract inside the pipeline. The contract is on the output side: it states what the published table promises. Some clauses repeat rules; that is deliberate.

The Open Data Contract Standard, v3.2.0

The schema part: one property per column the consumer uses

apiVersion: v3.2.0
kind: DataContract
id: bayyin-complaints-prepared
version: 1.0.0
schema:
- name: complaints_prepared
  properties:
  - name: complaint_id
    logicalType: string
    physicalType: VARCHAR
    required: true
    primaryKey: true
  - name: region_code
    ...
  • An open, vendor-neutral standard maintained by the Bitol project of the Linux Foundation.
  • Ten properties for the ten columns of today's table.
  • description says purpose, usage and limitations, in words.

The full contract is written by Lab 3.4 to artifacts/d3_4/contract.odcs.yaml; the reference copy is in data/reference. The physicalType values are the DuckDB types: DATE, DECIMAL(12,2), BIGINT, VARCHAR.

Quality clauses

A small library of metrics, or a SQL query that returns a number

- name: category
  quality:
  - metric: invalidValues
    arguments:
      validValues: [REFUND, DEFECT, DELIVERY,
                    PRICE, AD, WARRANTY]
    mustBe: 0
- name: amount_sar
  quality:
  - type: sql
    query: SELECT count(*) FROM ${object}
           WHERE ${property} > 50000
    mustBe: 0
  • Library metrics: nullValues, missingValues, invalidValues, duplicateValues, rowCount.
  • Operators: mustBe, mustBeGreaterThan, mustBeLessThan and their kin.
  • Six clauses in Lab 3.4, plus "required" on seven columns.

The metric names and the sql form are those of ODCS v3.2.0's data-quality section. The clauses carry Day 3's rules to the output side: U01, V01, V02, A01, K01 and a row count of more than 20,000.
