# Data Quality, Labelling and Pipelines for Analysis

جودة البيانات والتوسيم وخطوط إعدادها للتحليل

Data Science Track · SDAIA Academy · DS-311 · Level 300

Build the labels, rules, contract and gated pipeline an analysis depends on, and trace a figure that changed

Participants build the data an analysis depends on for Bayyin Consumer Protection Office, a fictional regulator holding 30,000 synthetic complaint records in Arabic and English. They write a labelling guideline, pilot it, measure agreement and adjudicate, run golden-question checks and review queues across a rater team, turn analysts' requirements into quality rules and a data contract, and package the preparation as a reproducible pipeline that stops on those rules. Measuring model-made labels is DS-306; platform-scale data engineering is AE-306.

**Format:** Intensive: 4 teaching days of four sessions and a capstone day, with guided pre-work and a tracked follow-up task

**Course page:** https://sdaiaacademy.github.io/ds-311/

## Case study

**Bayyin Consumer Protection Office** is a fictional regulator with 30,000 synthetic complaints in Modern Standard Arabic, Gulf dialect, English and code-switched text, four source tables and a monthly complaint rate per 100,000 residents that its analysts publish. Every lab works on it: a six-category labelling guideline piloted with three raters and revised from adjudication, a golden set and gold checks over six raters (one of whom drifts), severity rules and merchant matching on seeded defects, a data contract, and a preparation pipeline that quarantines, blocks and leaves lineage records good enough to explain why a published figure changed. All data is generated by `labs/prepare_data.py` with a fixed seed; the personal data in it is invented.

The capstone moves to a second synthetic case, the maintenance requests of Al-Ghadaf Municipality (`labs/capstone/`).

## Capstone

A labelled, quality-gated analysis table for a second synthetic case (municipal maintenance requests), in a public repository whose README reports agreement and rule results from two runs, defended in a ten-minute review in which the assessor seeds a defect

**Submission:** a public GitHub repository link: the labelling guideline with its change log, agreement from two pilot rounds, the rules and the ODCS contract, the pipeline with its lock file and CI workflow, run logs of two runs (one passing on clean data, one stopped by a seeded defect) and an incident note, with a README that reports agreement and rule results from the two runs. Then a ten-minute live review: the assessor seeds a defect in the data and the participant runs the pipeline from a clean checkout, catches it and traces it.

Rubric: guideline and agreement 25, rules and contract 25, pipeline 25, incident handling 15, reproducibility 10. The brief, the data generator and a README template are in `labs/capstone/`.

## Assessment, AI use and responsible use

- **Assessment:** a supervised AI-off check on agreement, quality dimensions and rules (20%); the capstone repository on the rubric above (60%); the live review of a defect the assessor seeds (20%). Passing needs 70% overall and at least 60% on the capstone rubric. Authenticity rests on the run logs and commit history, and on the live review, in which an unseen defect must be caught and traced. Certificate: completion with assessed work.
- **AI use:** AI-off for the supervised check and for the first lab of Days 1 and 3 (Labs 1.1 and 3.1). An assistant as a tutor in the other labs, explaining errors without writing the guideline. Full use in the capstone, defended live. Model pre-labels are checked by people, never accepted unseen.
- **Responsible use:** the synthetic complaints carry planted personal data that is masked and classified before any model call (Lab 2.4); agreement is reported by language and dialect; the guideline records who may label distressing content and for how long, and Lab 2.3 checks it.
- **Pre-work and follow-up:** about two hours before Day 1, and a follow-up task within four weeks that is tracked by its run logs (`labs/follow_up.md`).

## Tools

Each line is a capability; the examples are interchangeable.

- **Annotation tool:** Label Studio, Argilla, a spreadsheet with locked validation rules
- **Validation framework:** Pandera, Great Expectations, Soda Core
- **Data contract specification:** Open Data Contract Standard, contract checks compiled to SQL tests
- **Data processing and pipeline runner:** DuckDB or Polars with a task runner, Dagster with OpenLineage events
- **Language model for pre-labels, through a chat-completions style endpoint:** a locally served open-weight model, a free hosted open-weight model
